# Orbsie Plus waitlist

`POST /api/waitlist` accepts `{ "email": "person@example.com" }` without an account. It validates the email, trims whitespace and lowercases it; plus addressing is preserved. New and existing signups return HTTP 200 with `{ "joined": true, "confirmation": "sent" | "pending" }`, without exposing signup identity or whether a record already existed. `sent` means Resend accepted the confirmation, not inbox delivery. `pending` still means the signup was saved.

Apply `scripts/waitlist-schema.sql` to each environment's database. Set `RESEND_API_KEY` and `WAITLIST_EMAIL_FROM` (a verified Resend sender such as `Orbsie <hello@orbsie.com>`). Without either email setting, signups persist and no delivery attempt is consumed. The route requires `WAITLIST_RATE_LIMIT_SECRET` or the existing `BETTER_AUTH_SECRET`; absent database/hash configuration returns a generic 503 rather than claiming signup success.

Origin checks remain enabled. A maximum 2 KiB body is read. The shared database enforces five attempts per hour per HMAC-SHA256 IP bucket, with a 429 and Retry-After. The Vercel-owned `x-vercel-forwarded-for` header is used only when `VERCEL=1`; other hosts conservatively share an unknown bucket until a trusted ingress adapter is supplied. Raw IPs are neither persisted nor logged. Rate buckets older than one day are pruned on requests. This is a bounded basic throttle, not a CAPTCHA or distributed bot-defense system.

Email delivery has an atomic database claim, a 10-second provider timeout, and a fixed idempotency key based on the random signup ID. First-attempt content and sender are stored so retries use exactly the same payload. Confirmed signups are never resent. Pending attempts are spaced fifteen minutes apart, with five attempts maximum and a 23-hour retry window. The window deliberately fits inside [Resend's 24-hour idempotency retention](https://resend.com/docs/dashboard/emails/idempotency-keys). Unknown delivery outcomes older than this window require an operator to reconcile provider logs before any manual retry, preventing silent duplicate confirmations. A failed provider call or failed database acknowledgement never produces a sent claim.

After configuring email, an operator can run `node --env-file=.env.local scripts/flush-waitlist.mjs`. It processes at most twenty eligible existing signups, respects their claim/retry limits, paces requests, and reports aggregate counts without addresses or provider output. It does not reset exhausted/expired attempts. There is no public flush endpoint and no scheduler installed; signup retries or this operator command drive pending delivery.

The confirmation is a fixed inline-style table email with dark space colors, cyan orb, one Orbsie link, and plain-text fallback. It confirms interest only, with no price, promised launch date, subscription, or purchase. API details follow [Resend's send-email reference](https://resend.com/docs/api-reference/emails/send-email). No real delivery is claimed by deterministic tests or HTML preview. Sender DNS, inbox delivery and email-client-specific rendering require configured-service verification.
