# Browser modeling backend prototype — preliminary

An isolated temporary npm project installed exact `@bitbybit-dev/manifold-worker@1.1.1` and `manifold-3d@3.3.2` with lifecycle scripts disabled. The app package and lockfile were not changed. The retained prototype lock records dependencies for reproduction; it is not a completed distribution-license review.

The direct Node WASM probe passed: initial arch 152 triangles, volume 23.288210523297796; taller cutter result 136 triangles, volume 22.65263264294031. Both returned NoError and bounds [-3,-2,-0.75] to [3,2,0.75]. One local observation measured initialization 11.50 ms and combined construction/edit 7.96 ms. These are not browser or representative-device benchmarks. Every constructed Manifold object is explicitly deleted in finally.

To reproduce, create a temporary npm project, copy `prototype-package-lock.json` as `package-lock.json` with its matching root dependencies, install with `--ignore-scripts`, copy `direct-probe.mjs` alongside its node_modules, and run it with Node. The script checks valid geometry and reduced volume after the opening edit.

Still required: Bitbybit worker comparison, actual browser execution, recipe integration, output validation, rendering inspection, cancellation/resource bounds and full provider editing/export/publication. No backend selection has been finalized and no model inference was used.

Bitbybit comparison: its actual worker message handler (`initializationComplete` / `onMessageInput`) passed the same arch/edit geometry checks in Node. It returned 152 / 136 triangles, matching direct Manifold volumes and bounds, and NoError for both results. The probe uses cache handles and calls `cleanAllCache` in finally. One observation measured initialization 11.70 ms and construction plus inspection 10.04 ms; this includes different instrumentation from the direct probe and is not a comparative performance benchmark.

Reproduce `bitbybit-probe.mjs` in the same temporary project by bundling with esbuild (`--bundle --platform=node --format=esm --external:manifold-3d`) and running the resulting `.mjs` there. The unminified Node probe bundle was 344.6 KiB, excluding external Manifold; this is not production browser download size. No third-party bundled code is retained in the repository.

The adapter must convert Orbsie's radians to the backend rotation convention and restrict method dispatch to validated recipe operations. Bitbybit's generic dispatcher is an implementation detail, not an API to expose directly to model output. Browser worker lifecycle and cancellation are still untested by this probe.

Actual browser-worker check passed in headless Chromium: a module Worker loaded the locally served WASM, executed the arch/edit sequence twice in the same worker, cleaned its cache after each sequence, and returned matching 152/136 triangle counts, volumes and bounds with NoError. The main page recorded zero page errors. The test aborted non-local page requests. This is a geometry-worker check, not rendered Orbsie integration or a worker network-isolation guarantee.

`browser-worker.mjs` retains the source. Bundle for browser with esbuild `--bundle --platform=browser --format=esm --external:module`, serve the resulting worker with `manifold.wasm` beside it, and send two successive messages after its ready event. The external Node-only `module` import remains on the unexecuted Node branch. This setup passed without cross-origin isolation headers. The 449.1 KiB unminified bundle includes the adapter and JS runtime, not the WASM payload. The initial exploratory timing mixed initialization and elapsed job time; the retained worker and reproducible harness now capture initialization once before job dispatch. Production integration needs proper phase measurements, cancellation/resource tests and asset hosting checks.

Reproducible acceptance: `node scripts/verify-browser-modeling-prototype.mjs PROTOTYPE_NPM_DIRECTORY NEW_REPORT.json`. The script checks installed versions, bundles the source, serves only three local resources on an ephemeral loopback port, runs two real module-worker jobs with a deadline, checks geometry and browser errors, and writes the report without overwriting existing evidence. `browser-report.json` records the passing run. This still does not test the app, representative rendering performance, malicious-code isolation or interruption of an expensive geometry operation.

Direct browser comparison now also passes the same two-job geometry acceptance. `direct-browser-report.json` and `bitbybit-browser-size-report.json` record like-for-like browser harness runs. Unminified probe JavaScript: direct 108,134 bytes (22,595 gzip), Bitbybit 460,237 bytes (85,225 gzip). Both use the same 476,297-byte WASM (192,312 gzip). These are probe artifacts, not final app bundles; no production latency claim follows from two jobs.

Initial adapter decision: direct Manifold behind the Orbsie SDK, because the bounded recipe evaluator already needs its own validation, queue/cancellation and disposal contract and the direct prototype avoids the wrapper's generic dispatcher/cache layer. Bitbybit remains a viable alternative, with working worker evidence retained. Revisit after integrated lifecycle and responsiveness checks if its cache/API materially reduces implementation complexity. This decision follows the requested Bitbybit-first prototype, not an assumption that its API cannot work.

The harness accepts an optional final `direct` or `bitbybit` argument and records backend-specific bundle sizes plus common WASM sizes. Both backends retain local-only resources and the same exact geometry assertions.

Worker-to-storage integration: `node scripts/verify-browser-modeling-storage.mjs NEW_REPORT.json` builds the actual development worker and the real GLB/storage modules, serves them on an ephemeral loopback origin, constructs a boolean arch, bakes its mesh and material, saves it to IndexedDB as browser-manifold 3.3.2, reloads the page and reads/validates the same bytes and metadata. `storage-report.json` records the passing check with no page errors or blocked external requests. It bypasses the pending queue implementation and does not establish editor, provider, cloud or publication acceptance.

Queue integration now passes in the same real Chromium storage harness: an active dispatch and a queued request are cancelled with `aborted`, then a subsequent recipe completes, bakes, persists and survives reload. `storage-queue-report.json` retains the result. The cancellations occur immediately after dispatch, so this evidence proves queue cancellation/recovery, not interruption mid-boolean computation. Dedicated queue tests cover deadlines and malformed worker results separately.
